# Forecast engine v1: фактическая формула и воспроизводимый снимок

Этот документ фиксирует **уже исполненное** поведение `v1`. Он не описывает
желаемую модель `v2` и не пересчитывает исторические сигналы новой формулой.

## Область аудита

Цепочка `v1` находится в следующих функциях:

- разбор правил и диапазонов: `src/polybot/rules.py`;
- история станции и наблюдаемый максимум: `src/polybot/observations.py`;
- ensemble и вероятности: `src/polybot/weather.py`;
- связывание источников и выбор одного рынка события: `src/polybot/scanner.py`;
- стакан, комиссия, edge и EV: `src/polybot/risk.py` и `src/polybot/fees.py`.

Последний полностью воспроизводимый пример, завершившийся новым входом `v1`, —
Shenzhen, запуск `scan_runs.id=192` от **9 сентября 2026 года**. Все числа ниже
прочитаны из неизменяемых снимков SQLite до аварийного восстановления checkout,
а не получены повторным запросом к провайдеру.

## 1. Правила и расчётные сутки

Детерминированный парсер получил:

```text
location              Shenzhen
observation_date      2026-09-09
unit                  C
precision             whole degrees / 0 decimal places
station               Shenzhen Bao'an International Airport
station_id            ZGSZ
resolution source     https://www.weather.gov/wrh/timeseries?site=zgsz
station timezone      Asia/Shanghai
```

Детерминированный аудит был `tradeable=true`. Astra вернула
`tradeable=false` из-за неявного часового пояса расчётных суток и неуказанной
станции Weather Underground. Во время исполнения `v1` часовой пояс был проверен
по метаданным первичного источника, а NOAA-история была доступна и свежа. Поэтому
неясности стали предупреждениями, а не блокерами:

```text
RULE_TIMEZONE_VERIFIED_FROM_STATION_SOURCE
FALLBACK_SOURCE_AMBIGUOUS_PRIMARY_AVAILABLE
```

## 2. Наблюдения станции

Основной канал — данные WRH/Synoptic для **точного** station ID `ZGSZ`.
Aviation Weather Center используется только как перекрёстная проверка записей.

К моменту снимка в расчётные сутки станции попали 13 температур:

```text
UTC                         Asia/Shanghai             Temp °C
2026-09-08 16:00            2026-09-09 00:00             29
2026-09-08 17:00            2026-09-09 01:00             30
2026-09-08 18:00            2026-09-09 02:00             29
2026-09-08 19:00            2026-09-09 03:00             28
2026-09-08 20:00            2026-09-09 04:00             28
2026-09-08 21:00            2026-09-09 05:00             28
2026-09-08 22:00            2026-09-09 06:00             27
2026-09-08 23:00            2026-09-09 07:00             28
2026-09-09 00:00            2026-09-09 08:00             29

2026-09-09 03:00            2026-09-09 11:00             31

```

Для каждой записи сохраняются исходный payload, `observed_at_utc`, время первого
получения, revision hash, признак `COR`, AWC receipt time и AWC temperature.
В этом снимке:

```text
observed_max_c  = 32.0
displayed_max_c = 32
stale           = false
gaps            = []
cross-checks    = []
```

Отображаемая температура каждой записи вычисляется текущим кодом как

```text
display(T) = floor(T + 0.5)
```

после чего `displayed_max_c` — максимум этих целых значений. Непрерывный
`observed_max_c`, а не округлённое значение, используется как нижняя граница
распределения.

## 3. Ensemble и дневной максимум

`v1` вызывает Open-Meteo Ensemble API с параметрами:

```text
latitude     22.63926
longitude    113.81066
daily        temperature_2m_max
timezone     Asia/Shanghai
start_date   2026-09-09
end_date     2026-09-09
```

Локальный код **не строит максимум из почасовых рядов**. Провайдер уже возвращает
по одному `temperature_2m_max_member*` на участника ensemble.

Сохранённые 30 значений:

```text
34.4, 32.6, 34.0, 33.7, 33.0, 34.0, 32.1, 34.9, 33.0, 33.7,
33.1, 32.7, 34.1, 34.0, 34.7, 33.3, 34.6, 32.2, 33.9, 34.1,
33.6, 34.1, 33.5, 33.5, 33.6, 33.7, 33.0, 35.0, 32.8, 33.0
```

Их минимум — `32.1`, максимум — `35.0`, среднее —
`33.596666666666664°C`.

Состоявшийся максимум применяется к каждому участнику:

```text
adjusted_member[j] = max(raw_member[j], observed_max_c)
```

В этом примере все участники уже выше `32.0°C`, поэтому массив не изменился.

### Что известно о выпуске модели

Снимок хранит provider `open-meteo-ensemble`, географию, timezone, дату,
`fetched_at` и численные значения. Он **не хранит** конкретную исходную модель,
ID участника, model run/init time, provider publication time или hash полного
HTTP-ответа. Запуск воспроизводится из сохранённых чисел, но его нельзя связать
с доказанным исходным NWP-выпуском.

## 4. Диапазоны

`build_brackets()` берёт минимальный положительный шаг между метками. Здесь шаг
равен `1°C`, поэтому точная метка `k°C` означает полуинтервал `[k, k+1)`.

```text
27°C or below  (-∞, 28)
28°C           [28, 29)
29°C           [29, 30)
30°C           [30, 31)
31°C           [31, 32)
32°C           [32, 33)
33°C           [33, 34)
34°C           [34, 35)
35°C           [35, 36)
36°C           [36, 37)
37°C or higher [37, +∞)
```

Отдельная проверка запрещает вход, если уже отображённый максимум станции не
может попасть в диапазон:

```text
impossible(B) = B.upper is not None and displayed_max_c >= B.upper
```

## 5. Формула вероятностей

Для каждого скорректированного участника `mu_j` строится нормальное
распределение с фиксированной ошибкой:

```text
X_j ~ Normal(mu_j, sigma²),  sigma = 1.5°C
```

Пусть `O` — уже наблюдённый максимум, `B=[L,U)` — диапазон, а `Phi` — CDF
стандартного нормального распределения. `v1` условно обрезает распределение
снизу, потому что итоговый максимум не может стать меньше `O`:

```text
a = max(L, O)

q_j(B) = 0,                                            если U <= O
q_j(B) = [Phi((U-mu_j)/sigma) - Phi((a-mu_j)/sigma)]
         / [1 - Phi((O-mu_j)/sigma)],                  иначе

p(B) = (1/N) * sum_j q_j(B)
```

Результат каждого рынка округляется через `round(value, 10)`, затем
преобразуется в `Decimal`.

| 4321977 | 28°C | 0.0000000000 |

| 4321979 | 30°C | 0.0000000000 |

## 6. От вероятности к paper-решению

Для `market_id=4321983`, 34°C:

```text
book timestamp     2026-09-09T05:03:29.141Z
decision timestamp 2026-09-09T05:03:45.567407Z
book age           16.426407 seconds (< 180 seconds)
best ask           $0.03 × 126.3 shares
minimum order      5 shares
fill               5 shares × $0.03
VWAP                $0.03
probability         0.2410709517
```

```text
fee = 5 * 0.05 * (0.03 * 0.97)^1 = $0.007275
edge = 0.2410709517 - 0.03 = 0.2110709517
max_loss = 0.15 + 0.007275 + 0.02 = $0.177275
EV = 5 * 0.2110709517 - 0.007275 - 0.02 - 0.02289
   = $1.0051897585
```

Пороги `edge>=0.08`, `EV>=$0.25`, `max event risk<=$2.00` были выполнены.
Среди прошедших кандидатов события выбирается один рынок с максимальным EV,
поэтому 34°C стал `PAPER_BUY`.

## 7. Ограничения v1

1. Нет provenance исходного model run/init/publication и ID участников.
2. Все участники равно взвешены и используют общий `sigma=1.5°C`.
3. Наблюдение применяется дважды: к среднему участника и как truncation floor.
4. Используется готовый дневной максимум, а не почасовой путь остатка суток.
5. `[k,k+1)` и `floor(T+0.5)` требуют проверки для каждого источника, особенно
   для отрицательных температур.
6. Стаканы диапазонов не являются атомарным снимком одного момента.
7. Astra извлекает правила, но не генерирует вероятность.
8. До множества уникальных разрешённых событий вероятности нельзя считать
   откалиброванными.

## 8. Неизменяемость истории

Старые `paper_orders.strategy_version=v0` остаются `v0`, пример — `v1`.
Следующий алгоритм должен создавать новые versioned rows. Нельзя заменить
исходные probability, price, EV или version старой позиции новым пересчётом.

`tests/test_forecast_v1_regression.py` содержит автономную копию входов запуска
`192`. Тест не читает текущую SQLite и не обращается в сеть.
